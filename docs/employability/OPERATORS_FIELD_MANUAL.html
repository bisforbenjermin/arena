02

The Build Map

Five chains. One root. Everything downstream inherits the shape of F1, which is why it was frozen before anything else was written.

The rule this encodes

Freeze the interface before building against it. A contract settled early costs an hour; the same contract settled after three modules exist costs a rewrite of all three. Most engineers learn this from the rewrite.

03

Engineering → Business

This is the section that makes you an FDE rather than a coder. Every technical ruling traces to a business or legal requirement. Being able to draw that line out loud is the interview.

The sentence that carries this in an interview

"The platform's legal exposure turns on whether skill predominates over chance. That is not a policy question I can answer with a document — it has to be a property of the system. So scoring is deterministic and server-replayed, rank only accrues from verified real play above a participation threshold, and the bot harness produces a durable evidentiary record of the skill gradient. The compliance artifact is an output of the build, not a thing written alongside it."

Ecosystem gating

Five value-tiers (A–E), walled from each other, each with its own legal surface. A ships free with no gate. E may never ship. Containment by design.

Eligibility ≠ entitlement

Status makes a player eligible. It never entitles them to a payout and never converts to currency. One sentence that keeps the whole credit surface out of securities territory.

Audience ≠ prize cost

Broadcast reach stays decoupled from prize liability. The HQ Trivia lesson: when viewership drives cost, growth is the thing that kills you.

The Decision Ladder

The most expensive habit in solo building is treating a cheap decision like an expensive one. Classify first, then spend accordingly.

The ADR template

# <ID> — <short title>

**Ruled:** YYYY-MM-DD · **Reversibility:** REVERSIBLE | EXPENSIVE | LOCKED
**Undo cost:** <hours, or "rewrite">
**Confidence:** HIGH | MEDIUM | LOW

## Ruling
<one paragraph, unambiguous, written as a rule not a discussion>

## Why
<the reasoning, so it is not relitigated in six weeks>

## Downstream
<what now assumes this is true>
Provenance discipline

Record what you decided separately from what an assistant proposed. Six pre-rulings sat for eight weeks reading as frozen when they had only ever been suggested with defaults. An unruled default that everything is built on is the central unsolved problem in agent-assisted engineering — and knowing that firsthand is worth saying out loud.

05

The Gate Pipeline

Generate freely at the edges, gate hard in the middle, reserve human judgement for taste and canon. This is a defensible agent-system design philosophy and it is worth being able to state in one breath.

Where to put a human

Not at the start (you become the bottleneck) and not at the end (you rubber-stamp). Put them at the one judgement the system genuinely cannot make — here, taste and canon.

Why rejection is cheap

Each gate is ordered by cost: compile is cents, bot playtest is seconds, the LLM judge costs real money. Cheap gates first means expensive gates see fewer candidates.

06

Routing Work

Two separate dials, routinely confused. Model is how much it knows. Effort is how hard it tries. Cost follows consequence.

SymptomDialReasoning
Had full context,
tried, still wrong		Raise the modelCapability ceiling. More effort on the same weights produces a more thorough wrong answer.
Skipped files,
stopped early		Raise the effortEffort governs files read, tools run, steps taken before checking back.
Confused output,
wrong target		Fix the promptNeither dial rescues an unclear question. Most failures are here.
Expensive and
pre-reduced		Max effort, onceOnly after cheap passes have narrowed the surface. Never open at max on an unreduced problem.

Low effort

Mechanical work. File moves, enumeration, status updates, a rename. Anything a diff can verify at a glance.

Medium effort

Real work with a known shape. Writing a test, a staged migration, a build against a frozen spec. The default for most sessions.

Max effort

Changes to gates or decisions. Architecture that becomes load-bearing. Only on a surface that cheaper passes have already reduced.

Carried over

Effort does not transfer between sessions. Planning at max and then executing at low gives you a careful plan carried out carelessly. Put the thinking in a file, and give the execution session the effort the execution actually needs.

07

The Session Loop

Build for interruption, not for discipline. The old protocol put the expensive step at the moment of least energy, so it stopped happening and five weeks of rulings never landed in a file.

Close — ten seconds

YYYY-MM-DD | chain | stopped at: <where>
  | confused by: <what, or ->

Append only. Never regenerate anything at close. Commit, push, walk away.

Open — while fresh

Read the last ten log lines and the capsule. Rebuild state. Report three lines: where we are, what is next, what is blocked. Then stop — no project summary, no accomplishments list.

08

Standing Practice

What a tech role assumes you already do. None of it is difficult; all of it is visible in a repo within thirty seconds.

Version control

  • Atomic commits — one logical change each
  • type: summary under 50 chars, blank line, then why
  • Types: feat · fix · docs · test · chore · refactor
  • Never commit secrets; .env in .gitignore always
  • Branch per unit of work, merged by pull request — even solo

Testing

  • Unit · integration · end-to-end
  • A found bug becomes a regression test so it cannot return
  • Watch a test fail before making it pass
  • CI runs them on every push, not when you remember

Reproducibility

  • Pin dependencies; commit the lockfile
  • Deterministic builds — same input, same output
  • Environments described in files, not assembled by hand

Documentation

  • README: what is this, how do I run it, how do I test it
  • ADRs capture why; code already shows what
  • Supersede, never silently edit — a stale doc with no marker is a trap

Risky operations

  • Backup first, then verify the backup
  • Check preconditions before touching anything
  • Assert the result; never assume the command did what it said
  • Phases with hard stops, so a failure is contained
  • Never delete the original — supersede it

Working with agents

  • Verification over attestation — ask for a test, not an opinion
  • Never let an agent grade its own output
  • Long instructions go in a file, read in one line
  • Scope locks and explicit stop conditions
  • Track what you decided vs what the agent proposed
The structural fix beats the resolution

Two copies of the same repo existed for eight weeks because nothing marked the stale one. The fix was not more care — it was a tombstone file in the dead repo and a shell alias that makes the live one the only place you land. When you catch yourself resolving to be more careful, look for the structural change instead.

The RUNWAY contract

When a step causes friction, the walkthrough that unblocks it obeys all of this or it is not finished being written:

  • No preamble. Step 1 is the first thing on screen.
  • Assume nothing is installed and nothing is configured.
  • One action per step, each command in its own block.
  • Every step states an observable checkpoint — "you should see X".
  • Likely failures inline, in the step where they occur: "if you see Y instead → do Z".
  • Never ask a question that can be resolved by assuming the common case and saying so.
  • No forward references. If it is needed, it is in the step.
  • End with the exact next command. Never "let me know how it goes".

Friction log

Every walkthrough you needed is evidence that something upstream was underspecified. Three entries against the same document means that document gets amended, not walked through again. The log is the deliverable; the walkthrough is the side effect.
